## Goal

Add incremental, background reindexing triggered by Obsidian file events (edit, move, delete) with 1-second debouncing, so the vector database stays in sync with vault changes without user intervention.

## Requirements

### Functional Requirements

| ID | Requirement |
|----|-------------|
| FR-01 | The plugin must register Obsidian file event listeners for `file-modify`, `delete`, and `rename` events on markdown files. |
| FR-02 | On a **file-modify** event, the indexer must re-embed the changed file's content and update (delete old + insert new) the corresponding chunks in the vector store. |
| FR-03 | On a **file-delete** event, the indexer must remove all chunks whose `source` field matches the deleted file's path from the vector store, then persist. |
| FR-04 | On a **file-rename/move** event, the indexer must delete all chunks with the old source path, re-index the file at its new path, and persist. |
| FR-05 | All incremental operations must be **debounced** with a 1-second delay: the timer resets on each event, and indexing occurs only after 1 second of no change events for the same or different files. |
| FR-06 | The debounce queue must be **shared** across all file events — a single pending timer handles all changes that occur within the debounce window. |
| FR-07 | The vector store must be **persisted to disk** after each incremental operation (edit, delete, move) completes successfully. |
| FR-08 | Incremental operations must use the same chunking, embedding, and vector store APIs as the full reindex (no separate code path). |
| FR-09 | When the user triggers a **full reindex** (ribbon icon click) while an incremental change is pending in the debounce queue, the pending queue must be **cancelled** and the full reindex must start immediately. |
| FR-10 | Incremental operations must be **silent** — no `Notice` is shown to the user during background indexing. |
| FR-11 | The indexer must only begin listening for file events **after** it has been successfully initialized (i.e., after `#initialize()` completes and the vector store is ready). |

### Non-Functional Requirements

| ID | Requirement |
|----|-------------|
| NFR-01 | Debounce must use standard reset-on-each-event behavior (not a fixed delay from the last event). |
| NFR-02 | Each incremental operation must complete within a reasonable time (typically < 2 seconds for a single note) so it does not block Obsidian. |
| NFR-03 | Embedding calls during incremental operations must still respect the per-request delay to avoid overwhelming the LiteLLM proxy. |
| NFR-04 | The debounce timer must be properly **cleared** when the plugin unloads to prevent dangling references. |
| NFR-05 | Incremental operations must not interfere with an in-progress full reindex. |

## Scope

### In-scope
- Obsidian file event registration (`file-modify`, `delete`, `rename`)
- 1-second shared debounce for all file events
- Incremental reindex of modified files (delete old chunks + re-embed + insert)
- Chunk removal from vector store on file delete
- Chunk update + re-index on file rename/move (delete old, insert new)
- Vector store persistence after each incremental operation
- Cancellation of pending debounce queue on full reindex
- Quiet error handling (skip + log to console)
- Event listener cleanup on plugin unload

### Out-of-scope
- Search or query UI (RAG responses)
- User settings UI for debounce timing, event toggles, or embedding config
- Smart partial chunk updates (re-chunk only changed paragraphs) — full re-chunk of the file
- Multi-vault support
- Conflict resolution for merge conflicts in notes
- Manifest or drift-tracking file (no persistent index state beyond vector store)
- Retry logic for transient embedding failures (silent skip only)
- Automatic full index on first plugin load (keeps existing behavior)

## Context

PRD 001.01 implemented full reindex via ribbon icon click. The vector store (`src/rag/vector-store.ts`) already supports `removeChunk(id)` and `addChunks(chunks)`, making incremental updates structurally feasible. The `Indexer` class (`src/rag/indexer.ts`) currently exposes `reindex()` for full rebuilds only.

Obsidian plugins can register event listeners via `this.app.vault.on(event, callback)` and remove them via `this.app.vault.off(event, callback)`. The `TFile` object provides `path`, `basename`, and `stat.mtime` properties. The `rename` event provides both the old and new `TAbstractFile` references.

The embedding pipeline (chunker → embedder → vector store) is already designed as separate classes, so the same pipeline can be reused for incremental operations without duplication.

### New Methods on `Indexer`

```typescript
/**
 * Re-index a single file: delete old chunks for this source,
 * chunk the new content, embed, and insert.
 * @param file - The file object (provides path).
 * @param content - The current file content.
 */
public async reindexFile(file: TFile, content: string): Promise<{
  chunksCreated: number;
  embeddingsGenerated: number;
  errors: Array<string>;
}>;

/**
 * Remove all chunks for a given source file path.
 * @param filePath - The vault-relative file path.
 */
public async removeFile(filePath: string): Promise<void>;

/**
 * Handle a file rename/move: remove old chunks, re-index at new path.
 * @param oldPath - The previous vault-relative path.
 * @param newFile - The file object at the new path.
 * @param newContent - The current file content at the new path.
 */
public async renameFile(
  oldPath: string,
  newFile: TFile,
  newContent: string,
): Promise<{
  chunksCreated: number;
  embeddingsGenerated: number;
  errors: Array<string>;
}>;

/**
 * Cancel any pending incremental operations and clear the debounce queue.
 * Called when a full reindex is about to start.
 */
public cancelPending(): void;
```

### New Method on `VectorStore`

```typescript
/**
 * Remove all chunks whose source matches the given file path.
 * @param filePath - The vault-relative source path.
 */
public async removeBySource(filePath: string): Promise<number>;
```

### Debounce Architecture

```
File Event (modify/delete/rename)
        │
        ▼
   [Check indexer initialized?]
        │
   Yes  │  No → ignore event
        │
        ▼
   [Clear existing debounce timer]
        │
        ▼
   [Set new 1s debounce timer]
        │
        ▼  (after 1s of no events)
   [Process all pending changes in batch]
        │
        ▼
   [For each pending file: reindex / remove / rename]
        │
        ▼
   [Persist vector store after each operation]
```

Key design decisions:
- A single `setTimeout` / `clearTimeout` pair manages the debounce.
- A `Set<string>` accumulates pending file paths (or operations with their payloads).
- On each event: clear the timer, add the file to the pending set, start a new timer.
- When the timer fires: process all pending files, clear the set, clear the timer reference.
- `cancelPending()`: clear timer, clear pending set, set a flag that full reindex is in progress.

### Event Handler Wiring (in `main.ts`)

```typescript
// After successful initialization:
this.app.vault.on("modify", (file) => this.#onFileChange(file));
this.app.vault.on("delete", (file) => this.#onFileDelete(file));
this.app.vault.on("rename", (file, oldPath) => this.#onFileRename(file, oldPath));

// Cleanup on unload:
this.app.vault.off("modify", ...);
this.app.vault.off("delete", ...);
this.app.vault.off("rename", ...);
clearTimeout(this.#debounceTimer);
```

### Error Handling

- All incremental operations catch errors and log to `console.warn`.
- No notices are shown to the user.
- Failed files are silently skipped; their chunks remain in the store until the next full reindex.
- Embedding failures follow the same pattern as full reindex (skip chunk, log, continue).

### Deletion Strategy

For `removeBySource(filePath)`, use Orama's fulltext search to find all documents matching the source path, then remove each by ID. This is more efficient than iterating individual chunk IDs since the caller doesn't know the chunk IDs.
