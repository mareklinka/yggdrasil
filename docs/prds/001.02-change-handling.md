## Goal

Add incremental, background reindexing triggered by Obsidian file events (edit, move, delete) with 1-second debouncing, so the vector database stays in sync with vault changes without user intervention.

## Requirements

### Functional Requirements

| ID | Requirement | Status | Notes |
|----|-------------|--------|-------|
| FR-01 | The plugin must register Obsidian file event listeners for `file-modify`, `delete`, and `rename` events on markdown files. | ✅ Implemented | `ChangeTracker.registerEventListeners()` |

## Scope

### In-scope
- Obsidian file event registration (`file-modify`, `delete`, `rename`)
- 1-second shared debounce for all file events
- Incremental reindex of modified files (delete old chunks + re-embed + insert)
- Chunk removal from vector store on file delete
- Chunk update + re-index on file rename/move (delete old, insert new)
- Vector store persistence after each incremental operation
- Cancellation of pending debounce queue on full reindex
- Quiet error handling (skip + log to console)
- Event listener cleanup on plugin unload

### Out-of-scope
- Search or query UI (RAG responses)
- User settings UI for debounce timing, event toggles, or embedding config
- Smart partial chunk updates (re-chunk only changed paragraphs) — full re-chunk of the file
- Multi-vault support
- Conflict resolution for merge conflicts in notes
- Manifest or drift-tracking file (no persistent index state beyond vector store)
- Retry logic for transient embedding failures (silent skip only)
- Automatic full index on first plugin load (keeps existing behavior)

## Context

PRD 001.01 implemented full reindex via ribbon icon click. The vector store (`src/rag/vector-store.ts`) already supports `removeChunk(id)` and `addChunks(chunks)`, making incremental updates structurally feasible. The `Indexer` class (`src/rag/indexer.ts`) originally exposed `reindex()` for full rebuilds only, but was redesigned during implementation to use a unified queue-based processor.

Obsidian plugins can register event listeners via `this.app.vault.on(event, callback)` and remove them via `this.app.vault.off(event, callback)`. The `TFile` object provides `path`, `basename`, and `stat.mtime` properties. The `rename` event provides both the old and new `TAbstractFile` references.

The embedding pipeline (chunker → embedder → vector store) is already designed as separate classes, so the same pipeline can be reused for incremental operations without duplication.

## Technical Specification

### Architecture Overview

The implementation uses a **unified queue-based processor** architecture rather than the direct synchronous methods originally specified in this PRD. Both full reindex and incremental file operations enqueue work items that are processed sequentially by a single async processor loop in `Indexer`.

**Why this differs from the original spec:** The queue-based approach provides better concurrency handling, automatic deduplication of modify events, and a single processing path for all operations. The `ChangeTracker` delegates to `Indexer` via enqueue methods rather than direct async method calls.

### Class: `ChangeTracker` (`src/rag/change-tracker.ts`)

```typescript
export class ChangeTracker {
  // Private state
  #indexer: Indexer;
  #vault: { read: (file: TFile) => Promise<string>; getMarkdownFiles: () => Array<TFile> };
  #debounceTimer: ReturnType<typeof setTimeout> | null = null;
  #debouncePending: Array<PendingOperation> = [];
  #onModifyRef: ((file: TAbstractFile) => void) | null = null;
  #onDeleteRef: ((file: TAbstractFile) => void) | null = null;
  #onRenameRef: ((file: TAbstractFile, oldPath: string) => void) | null = null;

  // Public methods
  registerEventListeners(appVault: unknown): void;
  unregisterEventListeners(appVault: unknown): void;
  cancelPending(): void;
}
```

**`PendingOperation` interface:**
```typescript
interface PendingOperation {
  type: "modify" | "delete" | "rename";
  file: TFile;
  oldPath?: string;
}
```

### Class: `Indexer` (`src/rag/indexer.ts`)

Queue-based enqueue methods replace the direct async methods originally specified in this PRD:

| Original PRD Method | Actual Method | Notes |
|---------------------|---------------|-------|
| `reindexFile(file, content)` | `enqueueEdit(file)` | Enqueues to queue; deduplicates if same file already pending |
| `removeFile(filePath)` | `enqueueDelete(file)` | Enqueues delete operation by file reference |
| `renameFile(oldPath, newFile, content)` | `enqueueRename(oldPath, newFile, content)` | Enqueues rename with old path and new content |
| `cancelPending()` | `cancelPending()` | Same signature; clears queue and resets processing flag |
| `isInitialized()` | *(not implemented)* | No initialization guard exposed |
| `setReindexing(active)` | *(not implemented)* | `#isReindexing` flag managed directly in `main.ts` |

**Additional public methods not in original PRD:**
| Method | Description |
|--------|-------------|
| `isProcessing(): boolean` | Returns whether the queue processor is currently active |
| `getQueueLength(): number` | Returns the current number of items in the queue |

**Private queue processor:**
```typescript
#queue: Array<QueueItem> = [];
#processing = false;
#processNext(): Promise<void>;  // Sequential async loop
#processFileModify(file, content): Promise<void>;
#processFileDelete(filePath): Promise<void>;
#processFileRename(oldPath, newFile, content): Promise<void>;
```

### Class: `VectorStore` (`src/rag/vector-store.ts`)

```typescript
/**
 * Remove all chunks whose source matches the given file path.
 * Uses fulltext search to find matching documents, then removes each by ID.
 * @param filePath - The vault-relative source path.
 * @returns The number of chunks removed.
 */
public async removeBySource(filePath: string): Promise<number>;
```

**Implementation detail:** Uses Orama's `search(mode: "fulltext", term: filePath, properties: ["source"], exact: true)` to find all hits matching the file path, then iterates `hits` and calls `remove(orama, hit.id)` for each. Returns the count of removed documents.

### Architecture Diagram

```
File Event (modify/delete/rename)
        │
        ▼
   ChangeTracker.#enqueueFileEvent()
        │
        ├── [Clear existing debounce timer]
        ├── [Push operation to #debouncePending]
        └── [Set new 1s debounce timer]
        │
        ▼  (after 1s of no events)
   ChangeTracker.#processDebounceQueue()
        │
        ├── "modify" → indexer.enqueueEdit(file)
        ├── "delete" → indexer.enqueueDelete(file)
        └── "rename" → read content → indexer.enqueueRename(oldPath, file, content)
        │
        ▼
   Indexer.#processNext()  (sequential queue loop)
        │
        ├── "modify" → #processFileModify()
        │              1. Read content (if not pre-provided)
        │              2. Skip if empty/whitespace
        │              3. chunkText(content, path)
        │              4. embedder.embedMany(chunkTexts)
        │              5. store.removeBySource(path)
        │              6. store.addChunks(storedChunks)
        │              7. store.saveToDisk()
        ├── "delete" → #processFileDelete()
        │              1. store.removeBySource(path)
        │              2. store.saveToDisk()
        └── "rename" → #processFileRename()
                       1. store.removeBySource(oldPath)
                       2. #processFileModify(newFile, newContent)
                       3. store.saveToDisk()
        │
        ▼
   Error caught → console.error, continue to next item
```

### Debounce Lifecycle

1. **On each event:** `clearTimeout(timer)`, push operation to `#debouncePending`, set new 1s timer.
2. **Timer fires:** clear timer ref, process all pending operations by enqueueing to `Indexer`, clear `#debouncePending`.
3. **Full reindex:** `indexer.cancelPending()` clears queue; `#isReindexing` set in `main.ts`; full reindex enqueues all files via `enqueueEdit()`.
4. **Plugin unload:** clear debounce timer, remove all event listeners.

### Event Handler Wiring (in `main.ts`)

```typescript
// After successful initialization — DO NOT register earlier:
this.#changeTracker = new ChangeTracker(this.#indexer, {
  read: async (file: TFile) => this.app.vault.read(file),
  getMarkdownFiles: () => this.app.vault.getMarkdownFiles(),
});

// Register file event listeners as the last step of initialization
this.#changeTracker.registerEventListeners(this.app.vault);
```

**Critical ordering constraint:** File event listeners must be registered as the **last statement** in `#initialize()`, after the vector store is confirmed ready.

**Cleanup on unload:**
```typescript
public onunload(): void {
  this.#changeTracker?.unregisterEventListeners(this.app.vault);
}
```

### Error Handling

- All incremental operations catch errors and log to `console.error` / `console.warn`.
- No notices are shown to the user.
- Failed files are silently skipped; their chunks remain in the store until the next full reindex.
- Embedding failures follow the same pattern as full reindex (skip chunk, log, continue).
- The `#initialize()` method returns `void` — if it fails, an error is thrown and caught in `main.ts` before listeners are registered.
- `#processFileModify` reads content from vault if not pre-provided (supports both full reindex and incremental paths).
- `#processFileRename` throws `Error("Indexer not initialized")` if `#store` is null (defensive check).

### Deletion Strategy

For `removeBySource(filePath)`, use Orama's fulltext search with `properties: ["source"]` and `exact: true` to find all documents matching the source path, then remove each by ID. This is more efficient than iterating individual chunk IDs since the caller doesn't know the chunk IDs.

## Known Gaps / Follow-up Items

1. **FR-12 not implemented:** No `isInitialized()` method on `Indexer`. Event handlers in `ChangeTracker` do not assert initialization before enqueueing. This means if an event arrives before initialization completes, it would silently enqueue to an uninitialized queue rather than throwing.

2. **NFR-05 partial:** No guard prevents new events from being enqueued while a full reindex is in progress. The `#isReindexing` flag exists in `main.ts` but is not checked by `ChangeTracker` or `Indexer.enqueueEdit()`.

3. **Missing `VectorStore.removeBySource()` tests:** The method is implemented and used but has no dedicated unit tests.

4. **Missing integration tests:** All debounce, incremental flow, and persistence integration tests remain unwritten.

5. **`setReindexing()` not implemented:** The `#isReindexing` flag is managed directly in `main.ts` rather than via a method on `Indexer` as originally specified. This is simpler but removes encapsulation.
